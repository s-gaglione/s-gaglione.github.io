Design note

Generative UI needs a design system, not a blank canvas

Models can now return interfaces instead of paragraphs. The interesting question is not whether they can draw a screen, but which screens we let them draw.

By Sullivan Gaglione · November 2026

Beyond the wall of text

Ask a model to compare three suppliers and it will write three paragraphs. What you wanted was a table. Ask it to reschedule a meeting and it will describe the new time. What you wanted was a confirmation card with a button. Generative UI is the idea that the model’s output can be an interface: it chooses a component, fills it with data, and the product renders it.

Done well, this is the missing half of the intent paradigm. Language captures what the user wants; a generated component shows the result in a form that can be scanned, edited and confirmed.

Two ways to do it

Free generation. The model writes markup or code, and the product renders whatever comes back. It is flexible and impressive in demos. It is also inconsistent with the rest of the product, hard to make accessible, hard to test, and a security surface.

Constrained generation. The model picks from a catalogue of components the team already owns — card, table, form, chart, confirmation — and supplies typed data. The product renders its own components. Less freedom, far more trust.

For products people rely on, I would choose the second almost every time.

The design system becomes an API

Under constrained generation, the design system changes role. It is no longer only a library for designers and front-end engineers; it is the vocabulary the model speaks. Each component needs what an API needs: a clear name, a schema for its data, rules for when to use it, and examples. “Use a table when comparing more than two items on more than two attributes” is now an instruction for a model as much as a guideline for a person.

This is good news for design teams. The quality of the generated interface depends directly on the quality of the system: well-named components, sensible defaults, accessible primitives. Design debt now shows up as model behaviour.

Keep the human in the loop where it counts

A generated button that sends money is dangerous, unless it shows, before approval, who acts, on what, and with what consequences. The rule I use: the model may propose any component; only a person may commit anything with consequences. For an irreversible action, the preview and the explicit approval are not negotiable, since there will be no undo.

Test interfaces like outputs

If the model chooses the interface, the choice can be wrong. That means evaluation now covers UI too: for a set of representative requests, did the model pick the right component, fill the required fields, cite its sources, and stay within the allowed actions? These checks are cheap to automate once components have schemas, and they catch regressions when the model or the prompts change.

Where it is going

I expect the boundary between “the app” and “the assistant” to fade. Screens will be partly static and partly assembled on demand from the same components. The teams that do this well will not be the ones with the most creative model, but the ones with the clearest design system and the strictest rules about what the model may do with it.
